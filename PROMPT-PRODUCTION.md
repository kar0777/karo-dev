# Промт: довести Karo до продакшена за одну итерацию

Скопируй всё, что ниже разделителя, и отдай агенту в этой папке проекта.

---

## Роль и цель

Ты работаешь в `D:\проекты\karo-prikol` — проект **Karo**: облачная платформа с AI-агентом (Next.js 16 App Router, React 19, Postgres/Drizzle, опциональный Redis, песочницы Mock/Docker/Daytona/BYOS, биллинг Stripe/Mock, Vitest + Playwright, CI в `.github/workflows/ci.yml`). Проект уже умеет запускаться в **demo-режиме с нулём внешних креденшелов** — это фундамент бесплатного деплоя.

**Цель одной итерации:** довести проект до продакшен-уровня и подготовить (а где можешь — выполнить) деплой на полностью бесплатном стеке, чтобы от пользователя потребовалось минимальное число ручных шагов (только то, что физически требует его аккаунты).

**Целевая бесплатная архитектура:**

- **Vercel Hobby** — хостинг Next.js. SSE работает на Node runtime; `dockerode` и Docker-песочницы на serverless невозможны, поэтому прод-конфиг использует `SANDBOX_PROVIDER=mock` (встроенный симулятор). Реальное исполнение кода позже подключается через BYOS-воркер `worker/karo-worker.mjs` на машине пользователя — это бесплатный путь.
- **Neon** (бесплатный тариф) — Postgres. Миграции из `drizzle/` накатываются отдельным шагом/джобой.
- **Redis не обязателен** — приложение работает без него; опционально Upstash free, если решишь, что rate-limiting выигрывает от общего стора.
- **Vercel Cron** — для трёх идемпотентных эндпоинтов: `POST /api/admin/sandboxes/sweep`, `POST /api/cron/billing/auto-topup`, `POST /api/cron/billing/apply-pending`. Проверь актуальный лимит кронов на бесплатном тарифе; если их разрешено меньше трёх — добавь один батч-эндпоинт (например `POST /api/cron/tick` под `Authorization: Bearer $CRON_SECRET`), который внутри вызывает все три, и повесь один крон на него.
- **Email** — по умолчанию console-транспорт; опционально оставь закомментированный пример под Resend free tier.

## Правила работы

1. **Автономность.** Не задавай вопросов по ходу. Все решения принимай сам из перечисленных выше дефолтов; если появляется развилка, не покрытая промтом, — выбирай наименее инвазивный вариант и фиксируй его в отчёте. Всё, что физически может сделать только пользователь (аккаунты, вставка секретов), собери в один финальный чеклист.
2. **Ничего не выдумывай.** Перед изменением конфигов/кода читай фактические файлы. Не изобретай API Next.js/Drizzle/Neon/Vercel — проверяй по актуальным докам.
3. **Секреты.** Никогда не коммить `.env*` (кроме `.env.example`), не выводи значения секретов в логи и отчёт. Все генерируемые секреты (`ENCRYPTION_KEY`, `CRON_SECRET`, пароли сида) генерируй, показывай пользователю ровно один раз в финальном чеклисте и указывай, куда вставить.
4. **Доказательства.** Каждое изменение подтверждай прогоном: `npm run verify` (format → typecheck → lint → test → build) обязан быть зелёным в конце итерации. Плюс `npm run test:e2e`. Заведи `RUN-EVIDENCE.md` и записывай туда команду → код выхода → краткий итог по каждому шагу.
5. **Минимум риска.** Не добавляй тяжёлых зависимостей без веской причины. Не ломай существующие контракты API и схему БД; миграции — только аддитивные.
6. Git-репозитория в папке НЕТ. Инициализируй его (`git init`), убедись, что `.gitignore` покрывает `.env*`, `.next/`, `node_modules/` (он уже должен), сделай осмысленные коммиты по фазам.

## Фаза 0 — аудит

- Прогони `npm run verify` и `npm run test:e2e`; зафиксируй исходное состояние, всё красное почини.
- Пройди чеклист «перед выходом в прод» из README и раздел Known limitations — преврати в задачи всё применимое.
- Составь список пробелов: есть ли `/api/health` (liveness/readiness), security-заголовки в `next.config.ts`, rate limiting на auth-эндпоинтах, `robots.txt`/`sitemap.xml`, OG-метаданные маркетинговых страниц, кастомные 404/500, корректная обработка ошибок в route handlers.
- Проверь, что прод-режим в demo-конфиге безопасен для публичного URL: сид-пароли не дефолтные, demo-логин либо выключен, либо с одноразовым случайным паролем, админ не имеет публичного самостоятельного registration-пути в `/admin`.

## Фаза 1 — продакшен-харднинг

- **Безопасность:** security-заголовки (HSTS, X-Content-Type-Options, Referrer-Policy, Permissions-Policy, продуманный CSP для Next), rate limiting на `auth/*` и `register`, корректный `TRUST_PROXY_HOPS` за Vercel-прокси, отсутствие секретов в клиентском бандле (проверь `NEXT_PUBLIC_*`).
- **Наблюдаемость:** `/api/health` (проверка БД лёгким запросом), структурное логирование (`LOG_LEVEL`), page-level error boundaries.
- **SEO маркетинговых страниц:** метаданные, `sitemap.ts`, `robots.ts`, OG-изображение, favicon-набор.
- **Vercel-конфиг:** `vercel.json` (crons, регион ближе к пользователю), `.env.production.example` — МИНИМАЛЬНЫЙ набор переменных для demo-прода: `APP_URL`, `DATABASE_URL`, `ENCRYPTION_KEY`, `CRON_SECRET`, `SANDBOX_PROVIDER=mock`, `KARO_DEMO_MODE=true`, `RATE_LIMIT_DISABLED=false`, `LOG_LEVEL`, `SEED_*` (случайные). Всё остальное — опционально и закомментировано.
- **Кроны:** реализуй консолидацию эндпоинтов, если лимит тарифа того требует; каждый эндпоинт должен работать и от админ-сессии, и от `Bearer CRON_SECRET` (уже так по README — подтверди кодом).

## Фаза 2 — автоматизация деплоя

- GitHub Actions: добавь job деплоя (через `vercel` CLI + секрет `VERCEL_TOKEN`, который пользователь вставит один раз, ИЛИ задокументируй вариант «Import Git Repository» в UI Vercel — выбери основной путь сам) и job миграций против Neon (`drizzle/` уже коммитится).
- Добавь в README раздел «Deploy to Vercel (free)» с точными шагами и кнопкой Deploy (если осмысленно); создай `DEPLOY.md` — единственный файл, который пользователь читает руками.
- Подготовь локальную проверку прод-сборки: `next build && next start` с минимальным env (или docker compose prod) — убедись, что приложение реально стартует с `SANDBOX_PROVIDER=mock` и без Redis.

## Фаза 3 — финальная верификация

- Зелёный `npm run verify` + e2e.
- Опиши smoke-скрипт против прод-URL после деплоя (login → создать проект → прогнать демо-агента → SSE-стрим пришёл → health 200). Если пользователь уже вставил секреты и URL — выполни его сам; иначе оставь готовым к запуску одной командой.
- Lighthouse/размер бандла маркетинговой страницы — фиксируй цифры, грубых регрессий быть не должно.

## Что делает пользователь (единственные ручные шаги)

Собери это в финальный отчёт как нумерованный чеклист с точными значениями. По умолчанию это примерно: 1) залогиниться в GitHub и разрешить push (репо уже подготовлен мной); 2) создать Vercel через GitHub и импортировать репо; 3) создать Neon и скопировать `DATABASE_URL`; 4) вставить в Vercel готовый список env (ты даёшь его целиком, включая сгенерированные секреты); 5) нажать Deploy / запустить миграции; 6) опционально — домен и `VERCEL_TOKEN` для CI-деплоя.

## Формат финального отчёта

1. Что изменено (по фазам, файлами).
2. Доказательства: команды → коды выхода, суммарный результат verify/e2e.
3. Чеклист ручных шагов пользователя с копипастой значений.
4. Итоговая стоимость инфраструктуры (должно быть $0) и её ограничения (Vercel Hobby — некоммерческое использование; реальное исполнение кода — через BYOS-воркер).
5. Известные ограничения, оставшиеся осознанно (из Known limitations).
